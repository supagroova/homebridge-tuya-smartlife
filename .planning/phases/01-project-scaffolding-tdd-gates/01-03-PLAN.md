<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → repo | The default GITHUB_TOKEN is an ambient credential that must be least-privileged |
| CI/publish → npm registry | The publish step holds publish authority; tokens/provenance cross this boundary |
| local working tree → remote | /ship pushes commits; secrets in the tree could be staged accidentally |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Elevation of Privilege | GITHUB_TOKEN scope in ci.yml | mitigate | Top-level `permissions: { contents: read }` in ci.yml; publish job narrowed to `{ contents: read, id-token: write }` — least privilege per job |
| T-01-07 | Spoofing / Tampering | npm publish authenticity | mitigate | `npm publish --provenance` with `id-token: write` (npm Trusted Publishing) so published artifacts carry verifiable provenance; long-lived NPM_TOKEN is only the fallback |
| T-01-08 | Tampering | lockfile drift reaching CI | mitigate | CI runs `npm ci` (install only from the committed lockfile) before the gate, mirroring the Plan 02 local guard |
| T-01-09 | Information Disclosure | secrets staged by /ship | mitigate | /ship stages explicitly by path (no blanket add) and refuses on .env* / *.pem changes |
| T-01-SC | Tampering | GitHub Actions third-party refs | accept | Only GitHub-maintained actions (checkout, setup-node) pinned at @v4 are used this phase; no third-party marketplace actions introduced |
</threat_model>
