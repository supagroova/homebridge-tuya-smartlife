# Phase 10 Plan: Verification Submission Package

**Phase:** 10 — Verification Submission Package
**Plan:** 10-01
**Mode:** standard
**Requirements:** VER-02, VER-03, VER-05, VER-06, VER-15
**Primary Outputs:**

- `LICENSE`
- updated `package.json` / `package-lock.json` metadata
- `.planning/phases/10-verification-submission-package/10-VERIFICATION-ISSUE-DRAFT.md`
- GitHub Release `v1.0.0`
- `.planning/phases/10-verification-submission-package/10-01-SUMMARY.md`

## Goal

Prepare the repo and submission package so the Homebridge verification request can be opened with
accurate evidence and no known Phase 9 blockers.

Phase 10 is both a small release-hardening fix phase and a submission-writing phase. It should close
the three Phase 9 readiness gaps, refresh verification evidence, and produce the issue content for
the `homebridge/plugins` Plugin Verification Request.

## Assumptions

- The Homebridge request is opened as an issue in `homebridge/plugins`, not as a pull request.
- The npm package version under review remains `1.0.0`; do not publish a new npm version unless a
  verification-blocking package-content issue is discovered.
- A public GitHub Release should use tag `v1.0.0` to match the npm package version, even though the
  GSD milestone archive tag is `v1.0`.
- The Homebridge verified badge must not be added in Phase 10.
- An icon is optional. Unless the user supplies or explicitly requests one during execution, Phase 10
  should submit without an icon rather than creating a trademark-sensitive asset.

## Success Criteria

1. `LICENSE` exists at the repository root and matches the declared `Apache-2.0` package license.
2. `package.json` includes `repository`, `bugs`, and `homepage` fields pointing to the public GitHub repository, and `package-lock.json` is synchronized.
3. `make check` and `npm run release:check` pass after metadata/license changes.
4. `npm pack --dry-run --json` confirms the package still includes expected Homebridge assets and now includes `LICENSE`.
5. GitHub Release `v1.0.0` exists with release notes based on `CHANGELOG.md`.
6. A fresh GitHub Actions run on the current verification-prep commit passes Node `22` and `24`, or the summary records exactly why that evidence is not yet available.
7. `10-VERIFICATION-ISSUE-DRAFT.md` contains the exact values/answers needed for the Homebridge issue template.
8. `10-01-SUMMARY.md` records what changed, commands run, release URL, CI evidence, and whether the verification issue is ready to open.

## Tasks

### 1. Close Phase 9 Repository Gaps

Make the smallest repository changes needed by the Phase 9 audit:

- Add root `LICENSE` with Apache License 2.0 text.
- Add `repository`, `bugs`, and `homepage` to `package.json`.
- Run `npm install --package-lock-only` or an equivalent npm lockfile update if package metadata changes the lockfile.

Expected metadata:

```json
{
  "repository": {
    "type": "git",
    "url": "git+https://github.com/supagroova/homebridge-tuya-smartlife.git"
  },
  "bugs": {
    "url": "https://github.com/supagroova/homebridge-tuya-smartlife/issues"
  },
  "homepage": "https://github.com/supagroova/homebridge-tuya-smartlife#readme"
}
```

Do not add the Homebridge verified badge.

### 2. Validate Package And Repo Readiness

Run the local gates:

```bash
git diff --check
make check
npm run release:check
npm pack --dry-run --json --cache /private/tmp/homebridge-tuya-smartlife-npm-cache
npm view homebridge-tuya-smartlife@1.0.0 version dist-tags repository bugs license keywords --cache /private/tmp/homebridge-tuya-smartlife-npm-cache
```

Confirm:

- `LICENSE` appears in pack contents.
- `repository`, `bugs`, and `homepage` appear in local package metadata.
- npm still reports `1.0.0` as latest.
- No install lifecycle script was introduced.

### 3. Create / Verify GitHub Release `v1.0.0`

Create the GitHub Release if missing. Use `CHANGELOG.md` as the source of release notes and include
the key v1.0 points:

- Smart Life user-code and QR-code login through Homebridge custom UI.
- Tuya cloud discovery without per-user Tuya developer accounts.
- HomeKit support for switches, outlets, temperature/humidity sensors, basic binary sensors, and thermostats.
- Polling-based status refresh and offline handling.
- Known limitations: cloud-only, polling-only, v1 device focus.

Suggested command:

```bash
gh release create v1.0.0 --repo supagroova/homebridge-tuya-smartlife --title "v1.0.0" --notes-file /tmp/homebridge-tuya-smartlife-v1.0.0-notes.md
```

If tag `v1.0.0` does not exist, `gh release create` can create it from the current commit. Before
doing so, verify whether the current commit should be the release target. If the user prefers the
original npm-published commit as the target, stop and ask before creating the release.

After creation:

```bash
gh release view v1.0.0 --repo supagroova/homebridge-tuya-smartlife
```

### 4. Refresh CI Evidence

Push the verification-prep commit only with user approval, then collect a fresh CI run if available.
Do not push directly to `main` without confirmation.

Evidence commands after push or existing CI:

```bash
gh run list --repo supagroova/homebridge-tuya-smartlife --limit 10
gh run view <run-id> --repo supagroova/homebridge-tuya-smartlife --json conclusion,status,headBranch,headSha,displayTitle,jobs
```

If the phase is completed before a fresh CI run is available, mark the issue draft as ready except
for fresh CI evidence and route that to the final pre-submit step.

### 5. Prepare Verification Issue Draft

Create `.planning/phases/10-verification-submission-package/10-VERIFICATION-ISSUE-DRAFT.md` with:

- Plugin Name: `homebridge-tuya-smartlife`
- Link To GitHub Repo: `https://github.com/supagroova/homebridge-tuya-smartlife`
- Plugin Icon: omitted unless user supplies one.
- Dropdown answers:
  - Same/less functionality than existing verified plugin: `Yes` to “does not offer same nor less functionality”, with explanation in More Information.
  - Installs and does not start unless configured: `Yes`.
  - No TTY/non-standard startup parameters: `Yes`.
  - No analytics/tracking: `Yes`.
  - Files stored inside Homebridge storage directory: `Yes`.
  - No unhandled exceptions: `Yes`.
- More Information:
  - This plugin uses Smart Life User Code + QR device-sharing login.
  - It avoids per-user Tuya developer accounts and IoT Core trial renewals.
  - It is a maintained replacement path for abandoned `homebridge-tuya-web`, but with a different onboarding model.
  - v1 supports switches/outlets, temperature/humidity sensors, basic binary sensors, and thermostats.
  - Tokens are stored under the Homebridge storage directory and sensitive values are not logged.
  - CI and release evidence links.

### 6. Close Phase 10

Create `.planning/phases/10-verification-submission-package/10-01-SUMMARY.md` with:

- Files changed.
- Commands run.
- GitHub Release URL.
- CI evidence status.
- Whether the Homebridge issue is ready to open.
- Any remaining manual user action.

Update:

- `.planning/REQUIREMENTS.md`: mark VER-02, VER-03, VER-05, VER-06, and VER-15 according to actual outcome.
- `.planning/ROADMAP.md`: mark Phase 10 complete only if all success criteria are met or explicitly routed.
- `.planning/STATE.md`: route to Phase 11 only after the issue is opened or clearly ready for the user to open.

- Do not add the Homebridge verified badge.
