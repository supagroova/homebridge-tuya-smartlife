<task type="tdd">
  <name>Task 1: Write failing UI server tests</name>
  <action>
    Add Node tests around small exported server helper functions rather than requiring a running
    Homebridge UI process. Cover input validation, QR start response shape, poll success writing the
    token file to a provided storage path, and friendly error mapping for known Tuya QR errors.
  </action>
  <acceptance_criteria>
    - `node --test homebridge-ui/server.test.mjs` fails before server helpers exist.
    - Tests cover token status, QR start, QR poll success, token persistence path, and safe response shape.
    - Tests assert access tokens and refresh tokens are not returned to the UI.
    - Tests cover friendly mapping for pending, expired, failed, `E0020003` / designated-app, and region/endpoint mismatch style errors.
  </acceptance_criteria>
  <verify>
    <automated>node --test homebridge-ui/server.test.mjs</automated>
  </verify>
</task>

<task type="tdd">
  <name>Task 2: Implement UI server endpoints</name>
  <action>
    Add `@homebridge/plugin-ui-utils` and `qrcode` as runtime dependencies. Implement
    `homebridge-ui/server.js` with request handlers for QR start/status and token status. Reuse
    `dist/auth/qrLoginFlow.js` and `dist/auth/tokenStore.js` at runtime so GitHub installs do not
    compile on the Homebridge host. Keep `prepare` absent.
  </action>
  <acceptance_criteria>
    - Server exposes handlers for token status, QR start, and QR polling.
    - QR start accepts user code and endpoint, then returns a QR display payload without persisted credentials.
    - QR poll persists successful auth to `${homebridgeStoragePath}/tuya-smartlife-token.json`.
    - `package.json` runtime dependencies include the UI server/QR libraries needed on Homebridge.
    - `package.json` `files` includes `homebridge-ui` and does not define `scripts.prepare`.
  </acceptance_criteria>
  <verify>
    <automated>node --test homebridge-ui/server.test.mjs && npm run build && npm run release:check</automated>
  </verify>
</task>

<task type="auto">
  <name>Task 3: Implement the custom UI screen</name>
  <action>
    Create `homebridge-ui/public/index.html` with a compact Bootstrap-compatible setup screen:
    user code input, endpoint selector/input, start button, QR display, polling status, success
    state, and restart prompt. Use `homebridge.request(...)` for all server calls and avoid storing
    tokens in browser state.
  </action>
  <acceptance_criteria>
    - The UI uses plain HTML/CSS/JS and works without a frontend build step.
    - The UI can show not-connected, QR pending, success/connected, expired, and failed states.
    - On success, the UI tells the user to restart Homebridge.
    - The UI does not display or store access tokens, refresh tokens, or raw token JSON.
  </acceptance_criteria>
  <verify>
    <automated>npm run release:check && npm pack --dry-run --json</automated>
  </verify>
</task>
