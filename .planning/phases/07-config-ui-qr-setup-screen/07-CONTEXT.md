# Phase 7: Config-UI + QR Setup Screen - Context

**Gathered:** 2026-06-29

**Source:** Gap-focused `/gsd-discuss-phase 7 --gaps` after 07-01 completed

<domain>

## Phase Boundary

Phase 7 makes the plugin usable from Homebridge UI after install. It replaces the plain generated
schema-only settings view with a custom settings screen that can complete Smart Life QR login,
persist the token into Homebridge storage, and document the setup path for early testers.

In scope:

- Homebridge custom UI activation via `customUi: true` and a shipped `homebridge-ui/` bundle.
- QR login setup from the plugin settings modal using Smart Life user code and region/endpoint.
- UI server endpoints for QR creation, polling scan completion, token-status checks, and friendly
  error responses.
- Token persistence to `tuya-smartlife-token.json` under Homebridge storage.
- Package/release checks proving tarball/GitHub installs include `dist/`, `config.schema.json`, and
  custom UI assets without build-time work on the Homebridge host.
- README setup, supported-device, and troubleshooting documentation.

Out of scope:

- MQTT push updates, v2 device types, and per-device DP overrides.
- Replacing the Tuya-published HA-compatible client id/schema before the port works.
- Broad npm public release if user testing still needs tarball/branch installs.
- A polished multi-page onboarding app; v1 should be minimal and reliable.

</domain>

<decisions>

## Implementation Decisions

### QR Setup UI

- **D-01:** Use Homebridge custom plugin UI, not the static schema form, for QR setup. The static
  form cannot render and poll QR login cleanly.
- **D-02:** Keep the first UI compact: status panel, Smart Life user code input, endpoint selector or
  text input, "Start QR Login" button, QR display, polling state, success state, and restart prompt.
- **D-03:** Use Homebridge/Bootstrap-compatible plain HTML/CSS/JS for the first screen. Do not add a
  frontend build chain for Phase 7.
- **D-04:** Use `homebridge.request(...)` for UI-to-server calls. The browser must not call Tuya
  directly and must not store access or refresh tokens.

### QR Server Flow

- **D-05:** Implement `homebridge-ui/server.js` as a thin adapter over the existing compiled auth
  modules in `dist/auth/qrLoginFlow.js` and `dist/auth/tokenStore.js`.
- **D-06:** Server endpoints should cover:
  - token status / already connected;
  - QR start from `{ userCode, endpoint }`;
  - QR poll from `{ qrToken, userCode }`;
  - optional disconnect/delete-token only if it is cheap and testable.
- **D-07:** On QR success, persist the token with `FileTokenStore` to
  `${homebridgeStoragePath}/tuya-smartlife-token.json`, matching `TOKEN_FILE_NAME`.
- **D-08:** Return only safe status data to the browser. Never return access tokens, refresh tokens,
  or full token JSON to the custom UI.
- **D-09:** Friendly error mapping should explicitly handle QR pending/expired/failed states and
  known Tuya setup failures such as "designated APP" / `E0020003` and region/endpoint mismatch.

### Packaging And Install Path

- **D-10:** Do not use `prepare` or any install-time TypeScript build for GitHub/tarball installs.
  The Homebridge Pi has already shown npm's Git dependency preparation path can be killed under
  memory pressure.
- **D-11:** Keep committing generated `dist/` output while testing from GitHub/tarball branches.
  Release checks must enforce tracked `dist/index.js`.
- **D-12:** Extend release checks so package/git install contents include `homebridge-ui/server.js`
  and `homebridge-ui/public/index.html`.
- **D-13:** README should document the tarball install path for current PR testing and the eventual
  npm install path separately.

### Claude's Discretion

- The exact UI copy, CSS spacing, endpoint labels, and polling interval can be chosen pragmatically
  during implementation.
- The UI can show the QR as a data URL generated by the server or as client-rendered markup, provided
  the browser never receives persisted credentials.

</decisions>

<code_context>

## Existing Code Insights

### Reusable Assets

- `QrLoginFlow` already returns QR creation, pending/expired/failed states, and persists token on
  successful polling when given a `TokenStore`.
- `FileTokenStore` already performs atomic-ish save via temp file + rename and treats missing or
  invalid token files as unauthenticated.
- `TOKEN_FILE_NAME` is already the platform runtime contract for where Homebridge discovery loads
  auth state.
- `release-check.mjs` already validates package metadata, tracked `dist/index.js`, and `npm pack`
  contents; it is the right place to add custom UI asset checks.

### Established Patterns

- Production TypeScript modules under `src/` need Jest tests first.
- Node `.mjs` utility scripts use `node:test` and `node:assert/strict`.
- Homebridge glue can be thin, but reusable QR server helpers should be testable without launching
  Homebridge UI.
- Build output is plain CommonJS `dist/`; no bundler.
- GitHub/tarball testing requires committed `dist/` because low-memory Homebridge hosts should not
  compile the plugin during install.

### Integration Points

- `config.schema.json` with `customUi: true` makes Homebridge load the custom UI bundle instead of
  showing only the generated schema form.
- `homebridge-ui/server.js` is spawned by Homebridge UI when the settings modal opens and can use
  `this.homebridgeStoragePath` for token persistence.
- `homebridge-ui/public/index.html` runs in the settings iframe and communicates with the server via
  `window.homebridge.request(...)`.
- Platform discovery reads the same token file on Homebridge restart and logs actionable setup
  guidance when the token is missing.

</code_context>

<specifics>

## Specific Ideas

- First screen should optimize for "can I connect my Smart Life account right now?", not visual polish.
- Show a "Connected" state if the token file already exists so testers understand why no QR is shown.
- After successful login, tell the user to restart Homebridge because the running platform discovers
  devices on startup today.
- Include a troubleshooting note for the current test install command using the GitHub tarball URL
  instead of `git+https://...`, because npm's Git dependency preparation path was killed on the Pi.

</specifics>

<deferred>

## Deferred Ideas

- Homebridge-specific Tuya `client_id` / `schema` acquisition or blessing remains a release-hardening
  follow-up before broad/verified release.
- Live refresh of platform discovery immediately after QR success can be deferred; restart prompt is
  sufficient for v1 testability.
- Rich onboarding UX, localization, screenshots, and visual polish can follow after the QR path works.
- MQTT push, lights/covers/fans, scenes, and per-device DP overrides remain v2 scope.

</deferred>
