# Phase 9 Plan: Homebridge Verification Readiness Audit

**Phase:** 09 — Verification Readiness Audit
**Plan:** 09-01
**Mode:** standard
**Requirements:** VER-01, VER-05, VER-06, VER-07, VER-08, VER-09, VER-10, VER-11, VER-12, VER-13, VER-14
**Output Artifact:** `.planning/phases/09-verification-readiness-audit/09-VERIFICATION-CHECKLIST.md`

## Goal

Produce a review-ready evidence checklist proving whether `homebridge-tuya-smartlife` satisfies the
current Homebridge plugin verification requirements before opening the `homebridge/plugins`
verification request.

This phase is an audit phase. It should not make feature changes unless the change is purely
documentation for the audit itself. Any code/package/doc fixes discovered by the audit should be
captured as blockers or follow-up tasks for Phase 10 unless they are required to complete the
evidence artifact.

## Assumptions

- The package under review is `homebridge-tuya-smartlife@1.0.0`.
- The verification request is opened as a GitHub issue in `homebridge/plugins`, not as a pull
  request.
- Homebridge's currently supported Node LTS versions for verification are Node `v22` and `v24`.
- Network-backed checks such as `npm view`, `npm pack` from registry, `gh release view`, and GitHub
  Actions status may require approval/escalation during execution.
- A local `v1.0` GSD tag exists, but the public GitHub Release should likely use `v1.0.0` to match
  the npm version.

## Success Criteria

1. `.planning/phases/09-verification-readiness-audit/09-VERIFICATION-CHECKLIST.md` exists and maps every Homebridge verification requirement to evidence, status, and any blocker.
2. The checklist records the source URLs and checked date for the Homebridge requirements and issue template.
3. The audit verifies or flags GitHub Release status for `1.0.0`, repository visibility/issues, README/changelog/license, npm package metadata, and package contents.
4. The audit verifies or flags Node `v22` and `v24` support using local gates and/or GitHub Actions evidence.
5. The audit verifies or flags fresh install/startup behavior, Homebridge UI setup path, token storage path, logging/security posture, analytics absence, and handled-error posture.
6. `09-01-SUMMARY.md` records pass/fail outcome and routes any remaining blocker to Phase 10.

## Tasks

### 1. Refresh Official Verification Requirements

Collect the current Homebridge verification requirements from official sources:

- `https://github.com/homebridge/plugins#requirements`
- `https://github.com/homebridge/plugins#plugin-verification`
- `https://github.com/homebridge/plugins/blob/latest/.github/ISSUE_TEMPLATE/1_verification-request.yml`

Write the source date and source links into the checklist.

Expected checklist sections:

- General requirements
- Environment requirements
- Codebase requirements
- Repository/release requirements
- Project-specific notes

### 2. Repository And Release Readiness Audit

Check:

- GitHub repository is public and has issues enabled.
- README, CHANGELOG, LICENSE, package metadata, and repository URLs are present.
- `homebridge-tuya-smartlife@1.0.0` is published to npm.
- A GitHub Release exists for `1.0.0`; if not, record as a blocker.
- The package has no install/postinstall/preinstall scripts that modify the user's system.
- Package keywords include `homebridge-plugin`.
- Package includes `config.schema.json`, compiled `dist`, `homebridge-ui/public`, and `homebridge-ui/server.js`.

Suggested commands:

```bash
node -p "JSON.stringify(require('./package.json'), null, 2)"
npm view homebridge-tuya-smartlife@1.0.0 version dist-tags repository bugs license keywords
npm pack --dry-run
gh repo view supagroova/homebridge-tuya-smartlife --json isPrivate,hasIssuesEnabled,url
gh release view v1.0.0 --repo supagroova/homebridge-tuya-smartlife
rg "preinstall|postinstall|install" package.json package-lock.json README.md .github config.schema.json homebridge-ui src
```

### 3. Node 22 / Node 24 Gate Evidence

Collect compatibility evidence for both supported Node versions.

Preferred evidence:

- GitHub Actions matrix includes Node `22` and `24`.
- Latest CI run for the relevant commit passed.
- Local or CI `make check` and `npm run release:check` pass.

Suggested commands:

```bash
cat .github/workflows/ci.yml
node --version
make check
npm run release:check
gh run list --repo supagroova/homebridge-tuya-smartlife --limit 10
gh run view --repo supagroova/homebridge-tuya-smartlife --log
```

If local machine only has one Node version installed, do not fake the other result. Record the local
version plus CI evidence, or record a blocker for missing Node-version evidence.

### 4. Install And Startup Behavior Audit

Verify the package installs cleanly and stays inert until configured.

Check:

- Fresh npm install succeeds from registry.
- Unconfigured plugin startup is safe: no Tuya discovery/control starts without a saved token.
- Homebridge UI setup path is enough for initial configuration; no TTY flow is required.
- `config.schema.json` and custom UI are included in the packed package.

Suggested evidence:

- Existing remote Homebridge smoke test from v1.0 summary.
- `npm pack --dry-run` package contents.
- Source review of `src/platform.ts`, `src/platformDiscovery.ts`, `config.schema.json`, and `homebridge-ui/server.js`.
- Existing tests covering no-token behavior and UI status behavior.

Suggested commands:

```bash
rg "tokenStore.load|No Smart Life|requires Smart Life|customUi|schema|homebridgeStoragePath" src config.schema.json homebridge-ui README.md
npm test -- --runTestsByPath src/platformDiscovery.test.ts
npm run test:ui
```

### 5. Storage, Logging, Analytics, And Error Handling Audit

Check:

- Tokens/cache files are stored under Homebridge storage.
- No analytics/tracking calls exist.
- Default logs do not include user code, QR token, access token, refresh token, encrypted payloads,
  or request signatures.
- Debug logs are gated and redacted.
- Expected auth/discovery/polling failures are caught and logged without unhandled exceptions.

Suggested commands:

```bash
rg "analytics|telemetry|tracking|segment|sentry|posthog|mixpanel|google-analytics|fetch\\(" src homebridge-ui README.md package.json
rg "accessToken|refreshToken|access_token|refresh_token|encdata|X-sign|X-token|userCode|qrcode|qrToken" src homebridge-ui README.md
npm test -- --runTestsByPath src/auth/customerApi.test.ts src/auth/qrLoginFlow.test.ts src/platformDiscovery.test.ts
npm run test:ui
```

Record positive test names as evidence where possible. If a risk is only proven by source review,
mark it as source-reviewed rather than test-proven.

### 6. Produce Checklist And Summary

Create:

- `.planning/phases/09-verification-readiness-audit/09-VERIFICATION-CHECKLIST.md`
- `.planning/phases/09-verification-readiness-audit/09-01-SUMMARY.md`

Checklist row format:

```markdown
| Requirement | Status | Evidence | Blocker / Follow-up |
|-------------|--------|----------|---------------------|
| Published to npm | Pass | `npm view ...` returned `1.0.0` | — |
```

Use statuses:

- `Pass`
- `Fail`
- `Blocked`
- `Needs Follow-up`

Summary must include:

- Overall readiness verdict.
- Commands run.
- Any network-backed checks that could not be run.
- Any Phase 10 fixes or release tasks required before submission.

## Verification Gates

Before closing Phase 9:

```bash
git diff --check
make check
npm run release:check
```

If `make check` or `npm run release:check` cannot run because of environment/network constraints,
record the exact reason in `09-01-SUMMARY.md` and keep the phase open or mark the blocker explicitly.

## Non-Goals

- Do not open the Homebridge verification request in Phase 9.
- Do not add the Homebridge verified badge in Phase 9.
- Do not change package functionality unless the user explicitly approves converting an audit finding into a fix.
- Do not claim Homebridge verification until the Homebridge team approves the plugin.
