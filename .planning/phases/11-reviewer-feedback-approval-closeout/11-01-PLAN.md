# Phase 11 Plan: Reviewer Feedback & Approval Closeout

**Phase:** 11 — Reviewer Feedback & Approval Closeout
**Plan:** 11-01
**Mode:** standard
**Requirements:** VER-04, VER-16
**Primary Outputs:**

- `.planning/phases/11-reviewer-feedback-approval-closeout/11-FEEDBACK-LOG.md`
- `.planning/phases/11-reviewer-feedback-approval-closeout/11-01-SUMMARY.md`
- README verified badge change only after Homebridge approval

## Goal

Track the Homebridge verification request from submission through reviewer feedback and approval,
making only the fixes reviewers require and adding the verified badge only after approval is granted.

## Preconditions

Before execution can fully complete:

- The Homebridge verification request issue must exist in `homebridge/plugins`.
- The issue URL must be recorded in the feedback log and Phase 11 summary.
- The latest Phase 10 closeout commit should be pushed, or Phase 11 should explicitly record that
  only local planning state is ahead.

If the issue has not been opened yet when Phase 11 execution starts, create the feedback log with
status `waiting-for-submission`, record the blocker, and stop before claiming Phase 11 complete.

## Success Criteria

1. `11-FEEDBACK-LOG.md` records the Homebridge verification issue URL, current status, reviewer comments, required actions, and outcomes.
2. Each reviewer request is classified as `accepted`, `clarification`, `not required`, or `deferred with rationale`.
3. Any accepted code/docs/package fix is implemented through the normal gates: failing/relevant test where applicable, `make check`, `npm run release:check`, and release/publish steps if package contents change.
4. Any reviewer-required release is linked back to the verification issue.
5. README receives the Homebridge verified badge only after approval is granted.
6. `VER-04` and `VER-16` are marked complete only after approval and closeout are real, not anticipated.
7. The milestone closes with a durable record of the final Homebridge verification outcome.

## Tasks

### 1. Capture Submission State

Create `.planning/phases/11-reviewer-feedback-approval-closeout/11-FEEDBACK-LOG.md`.

Required fields:

```markdown
# Phase 11 Feedback Log

**Verification issue:** <url or pending>
**Status:** waiting-for-submission | submitted | changes-requested | approved | rejected | withdrawn
**Submitted:** <date or pending>
**Last checked:** <date>

## Timeline

- <date>: <event>

## Reviewer Requests

| ID | Source | Request | Classification | Action | Status | Evidence |
|----|--------|---------|----------------|--------|--------|----------|

## Decisions

- <decision>
```

If the issue URL is not known:

- Set status to `waiting-for-submission`.
- Point to `../10-verification-submission-package/10-VERIFICATION-ISSUE-DRAFT.md`.
- Do not add badges or mark Phase 11 complete.

### 2. Monitor Reviewer Feedback

Use GitHub issue comments and labels as the source of truth.

Suggested commands after the issue URL is known:

```bash
gh issue view <issue-number> --repo homebridge/plugins --comments --json number,title,state,labels,comments,url
gh issue view <issue-number> --repo homebridge/plugins --json state,labels,url
```

Record:

- Whether Homebridge reviewers accepted the request.
- Any requested code/doc/package changes.
- Any question that requires clarification rather than a code change.
- Whether the existing npm `1.0.0` tarball missing the later-added root `LICENSE` is acceptable, or whether a patch release is required.
- Whether the Home Assistant compatible Tuya QR credential is acceptable for verification, or whether reviewers require a Homebridge-specific credential.

### 3. Implement Required Fixes Only

For each accepted reviewer request:

1. Add/adjust tests first when behavior changes.
2. Make the minimal code/docs/package change.
3. Run relevant targeted tests.
4. Run full gates:

```bash
git diff --check
make check
npm run release:check
```

If a package-content change must be published:

- Decide patch version, likely `1.0.1`.
- Update `package.json`, `package-lock.json`, and `CHANGELOG.md`.
- Run `make publish-check`.
- Publish manually unless the user explicitly changes the release process.
- Create a matching GitHub Release.
- Link the release in the verification issue and feedback log.

### 4. Close Approval

Only after the Homebridge team approves verification:

- Add the verified badge to `README.md`:

```markdown
[![verified-by-homebridge](https://badgen.net/badge/homebridge/verified/purple)](https://github.com/homebridge/homebridge/wiki/Verified-Plugins)
```

- Run:

```bash
git diff --check
make check
npm run release:check
```

- Commit the badge/update with a clear message.
- Push only with explicit approval if pushing to `main`.
- Update the feedback log with approval evidence and badge commit.

### 5. Close Phase And Milestone

Update:

- `.planning/REQUIREMENTS.md`: mark `VER-04` and `VER-16` complete only after approval.
- `.planning/ROADMAP.md`: mark Phase 11 complete only after approval or explicit milestone closure decision.
- `.planning/STATE.md`: route to `/gsd-complete-milestone` when verification is approved and closeout is committed.
- `.planning/phases/11-reviewer-feedback-approval-closeout/11-01-SUMMARY.md`: record issue URL, outcome, commands run, commits, releases, and remaining follow-ups.

## Verification Gates

Before Phase 11 can be marked complete:

```bash
git diff --check
make check
npm run release:check
```

If no code/package/docs changed during review, still run at least:

```bash
git diff --check
```

and record why full gates were not repeated.

## Non-Goals

- Do not add the Homebridge verified badge before approval.
- Do not publish a patch release unless reviewer feedback or package verification requires it.
- Do not broaden device support, add MQTT, or change Tuya credential strategy unless Homebridge reviewers make it a verification condition.
- Do not push to `main` without explicit approval.
